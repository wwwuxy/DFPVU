# Ara 四个 VMFPU 计算单元的 45 ns OpenROAD 硬件开销数据

## 测试边界与来源

本测试从上游 Ara 修订 `34bd3bc1` 中抽取四个真实的 lane-local `vmfpu` 实例。综合顶层以 `NrLanes=4`、`VLEN=4096` 为参数，每个 lane 实例化一个 `vmfpu`。封装保留了 `vmfpu` 内部的操作、操作数、掩码、结果、归约和异常接口，以及 IEEE 浮点、整数乘法、定点运算、队列和控制逻辑；不包含向量寄存器文件、访存单元、调度器、存储器接口和 lane 间互连。因此，测量对象是 Ara 的算术单元边界，而不是完整 Ara 加速器。

实现采用 OpenROAD-flow-scripts 的 `nangate45` 平台，在物理端口 `clk_i` 上施加 45.00 ns 的 `ara_clk` 约束，目标 core 利用率为 55%。封装顶层共有 31 个端口和 2,330 个端口位，布局阶段插入的端口缓冲仅计入物理实现阶段。Slang 展开参数为 `--unroll-limit=20000`。默认 Yosys 资源共享过程在 281 s 的受限运行内未生成检查点，因此可复现实验设置 `SYNTH_ARGS=-noshare`。该设置仅用于综合工具的可扩展性，不改变 Ara RTL；综合检查报告 0 个问题。

## 物理筛选边界

完成的 CTS 点是受限的物理筛选实现，不是布线完成的 PPA 流程。该流程保持 RTL、Nangate45 库、45 ns 时钟、floorplan 和 CTS 构建，但设置 `GPL_TIMING_DRIVEN=0`、`GPL_ROUTABILITY_DRIVEN=0`、`SKIP_CTS_REPAIR_TIMING=1` 和 `ENABLE_DPO=0`。这些控制项避免独立封装的大量端口引发无界物理优化。全局布局检查点被复用于 resize 输入，阶段 3 的报告汇总仅在这一复用路径上跳过。

由于有意跳过时序修复，CTS 报告仍有 11,975 个 hold 违例和 1,401 个最大电容违例。4.10 ns 最小周期和 setup WNS 只能作为诊断信息，不能代表可达到的工作频率。该边界没有全局布线、详细布线、布线后时序、DRC、布线长度/过孔、workload 活动功耗、能耗或签核结果。0.381 W 的功耗估计采用默认活动率，而非 workload VCD/SAIF，不能与其他功耗估计直接比较。

## 与 DFPVU 的关系

相对于完整 Ara 加速器，这个边界更接近 DFPVU `PvuTop`：两者均不含 Ara 的向量寄存器文件、访存路径、调度器和互连。在相同的 Nangate45、45 ns 和 55% floorplan 策略下，DFPVU `PvuTop` 的映射面积为 0.541908 mm²，四个 Ara `vmfpu` 的映射面积为 0.748853 mm²。这些数值是同一实现阶段的原始观测，可在同一张表中并列展示。

DFPVU/Ara 面积比或优劣结论仍未定义。`PvuTop` 实现了 DFPVU 的 Posit/IEEE 向量数据通路；Ara `vmfpu` 包含面向 IEEE 的 FPU/乘法器、单元内队列和控制，以及 half/single/double 支持。二者的指令集、精度支持、微结构和语义覆盖范围均不相同。若要论证共同算术操作的开销，应在同一物理阶段和活动率假设下，补充受约束的 FP32 操作级实验或 DFPVU 的 IEEE-only 消融实验。

## 可用于 IPDPS 的表述

*为将 Ara 的算术单元开销与完整加速器开销区分开，本文在 Nangate45 平台、45 ns 目标周期和 55% core 利用率下综合了四个 lane-local `vmfpu` 实例。该边界映射为 637,539 个标准单元，映射面积为 0.748853 mm²，包含 29,568 个 DFF 类单元；在 1.360489 mm² 的 floorplan 中，布局和 CTS 单元插入后的面积为 0.762037 mm²。该边界排除了 Ara 的向量寄存器文件、访存路径、调度器和互连。它可为 DFPVU `PvuTop` 提供算术边界的原始参照，但格式支持、操作覆盖范围和单元内控制的差异不支持面积或 PPA 优劣比。*
